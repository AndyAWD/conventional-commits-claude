# Type 對照表 + 撰寫指南

## Type 快速對照

| type       | 用途                | 中文範例                              |
|------------|---------------------|---------------------------------------|
| `feat`     | 新功能              | `feat(auth): 新增 OAuth 登入支援`     |
| `fix`      | 修 bug              | `fix(parser): 修正巢狀陣列解析錯誤`   |
| `docs`     | 文件                | `docs: 補上安裝步驟說明`              |
| `style`    | 格式（不影響行為）  | `style: 統一縮排為兩空格`             |
| `refactor` | 重構                | `refactor(api): 抽出共用錯誤處理`     |
| `perf`     | 效能                | `perf: 快取查詢結果減少重複計算`      |
| `test`     | 測試                | `test: 補上邊界條件測試`              |
| `build`    | 建置系統            | `build: 升級 vite 至 5.0`             |
| `ci`       | CI 設定             | `ci: 加入自動化部署工作流程`          |
| `chore`    | 雜項                | `chore: 更新 .gitignore`              |

## 如何選 Type

依決策順序：

1. **新增了「使用者可見」的能力嗎？** → `feat`
2. **修正了原本不正確的行為嗎？** → `fix`
3. **只改文件？** → `docs`
4. **只改格式，行為完全一致？** → `style`
5. **重整結構、不改變行為也不修 bug？** → `refactor`
6. **改善速度/記憶體？** → `perf`
7. **改測試檔案？** → `test`
8. **改建置設定 / 相依套件？** → `build`
9. **改 CI 設定？** → `ci`
10. **其他不影響 src 或 test 的雜項** → `chore`

## Scope 撰寫指南

- **可選**：不確定或涵蓋範圍太廣時可省略
- **使用名詞**：模組名、套件名、檔案主題（如 `auth`、`parser`、`api`、`config`）
- **小寫**：避免大寫、避免混合大小寫
- **簡短**：≤ 15 字元；用單一字詞或短連字號串接
- **一致性**：同一個模組的 commit 應用相同的 scope

**好的 scope**：`auth`、`parser`、`api`、`i18n`、`db`、`http`、`build`

**差的 scope**：`Login System`（含空白且大寫）、`the-thing-that-handles-users`（過長）、`fix`（type 而非位置）

## Description 撰寫要點

- **動詞開頭**：新增、修正、移除、更新、重構、優化...
- **繁體中文**（此 skill 預設）
- **不加句號**
- **≤ 50 字元**（GitHub PR 標題預設寬度）
- **具體**：說明「做了什麼」，避免「修正 bug」「更新程式」這類無資訊描述

**好**：`fix(cache): 修正 TTL 為 0 時直接回傳 null 的錯誤`
**差**：`fix: 修 bug`

## Body 撰寫要點

- **可選**，但涉及非顯而易見的動機時強烈建議填寫
- **說明「為何」而非「做什麼」**（diff 已能說明做什麼）
- 可分段、可包含背景與取捨
- 每段之間空一行

**好的 body 範例**：

```
feat(auth): 新增 OAuth 登入支援

現有 email/密碼流程對非技術使用者摩擦太大，客服反饋前三大流失點就是註冊。
提供 Google/GitHub OAuth 可讓多數使用者一鍵登入，同時保留原有流程給不願授權的人。
```

## 常見組合

- 新功能與 test 一起 → 通常合併為 `feat`（test 是實作的一部分）
- 修 bug 與 test 一起 → 通常合併為 `fix`
- Refactor 與新功能一起 → 通常拆開（不同 type）
- Format 修改與功能變更一起 → 通常拆開（`style` 獨立成 commit）
